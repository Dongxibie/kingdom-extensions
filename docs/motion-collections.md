# 双集合与候选池 / Collections & Candidate Pipeline

> Motion Lab 2.0 的两件事：把资源库分成 **Official 与 Community 两个集合**，
> 并把「GitHub 发现 → 规则分析 → 人工筛选 → 转成 Motion Pattern」做成一条真正走得通的流水线。

## 两个集合，一条纪律

| | Official Collection | Community Collection |
| --- | --- | --- |
| 数量 | 30 | 30 |
| 来源 | 本项目设计并实现 | 从社区案例里**发现**，由本项目重新实现 |
| 标注 | 来源标记为官方 | 带「灵感来源地址 + 来源许可」标注 |
| 实现归属 | 本项目 | 本项目（**不是复制第三方代码**） |

**这条纪律是这个模块的立身之本**：GitHub 只承担两件事 —— 发现优秀案例、学习实现思路。
候选池里存的只有**元数据**（仓库名、地址、说明、语言、星数、许可、主题），一行第三方代码都没有；
进入资源库的每一个 Pattern，CSS / Vue / React / Three.js 与预览结构都是本项目自己写的。

## 七分类

文字动画 / 卡片交互 / 按钮交互 / 滚动动画 / 首屏动画 / 背景效果 / 三维 WebGL。
分类、触发方式（加载时 / 悬停 / 滚动 / 点击）、运行档位（轻量 / 均衡 / 依赖 GPU 加速）三套维度可以叠加筛选。

| 分类 | 数量 | 分类 | 数量 |
| --- | --- | --- | --- |
| 卡片交互 | 12 | 文字动画 | 8 |
| 背景效果 | 11 | 按钮交互 | 7 |
| 首屏动画 | 10 | 滚动动画 | 7 |
| 三维 WebGL | 5 | | |

## 候选池：四步流水线

```
GitHub 发现          规则分析              人工筛选              转成 Pattern
─────────────  →  ─────────────  →  ─────────────  →  ─────────────────────
19 个查询            关键词权重表          状态机：               指定一个内置 Pattern
按星数排序           分类 / 触发 / 难度     待看 → 已分析          代码来自 Pattern
区间间隔 + 限流纪律   运行档位 / 视觉分      → 已选入 / 已淘汰      候选只提供名字、来源、许可
只取元数据           命中词留痕（可解释）   淘汰必须写理由         （幂等：已入库的直接返回）
```

**当前状态**：118 条候选 —— 已入库 30 / 已分析 50 / 已淘汰 38。

淘汰不是「不想要」，而是逐条写明理由：语言不对（Swift / Java / Kotlin 这类不是前端动效实现语言）、
清单类仓库（没有单一模式可提炼）、关键词未命中（无法归档）、星数过低。这些理由都留在候选表里，后续可以复盘。

## 为什么分析用规则、不用模型

这一步要的是**可复现、可解释、不花钱**：同一个仓库任何时候分析出来的分类都一样，而且能说出「因为命中了 text / typewriter」。
换成模型就会出现同样的输入两次不同结果，反而不好解释。需要模型的地方是动效助手 —— 那里要的是理解自然语言，不是归类。

## 转换接口的边界

`POST /api/motion/candidates/{id}/promote` 的入参里有且只有一个必填项：`patternTemplateKey`。
它做的是「换名字、贴来源」：把候选的名字、来源地址、许可写到指定 Pattern 的实现上，生成一条 Community 模板。
接口不接受任何外部代码，也从不读取候选仓库的源码 —— **这条限制写在方法注释里，也有单测钉住**。

## 数据与接口

- 表：`motion_candidate`（候选池，只存元数据）；`motion_template` 增加 `trigger_type` / `source_url` / `source_license`
- 接口：候选分页、概览统计、重新分析、人工筛选、转成模板（5 个）
- 种子可重复执行，且**不覆盖人做过的判断**：重跑种子只刷新「发现到的事实」，`status` / `review_note` / 已转 Pattern 保持不动
